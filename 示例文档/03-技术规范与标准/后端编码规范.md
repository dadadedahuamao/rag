# 后端编码规范（Python / FastAPI）

## 一、总则

本规范适用于公司所有基于 Python 的后端服务，旨在统一编码风格、提升可读性与可维护性，降低协作成本。规范以 PEP 8 为基础，结合团队实践进行约定。

## 二、命名规范

- 变量、函数、模块：小写下划线，如 `user_id`、`get_user_by_id`。
- 类名：大驼峰，如 `KnowledgeBaseService`。
- 常量：全大写下划线，如 `MAX_UPLOAD_SIZE`。
- 私有成员：单下划线前缀，如 `_internal_cache`。
- 命名应见名知意，避免使用 `data`、`tmp`、`x` 等无意义名称。

## 三、代码风格

- 缩进使用 4 个空格，禁止使用 Tab。
- 单行长度不超过 100 字符。
- 导入顺序：标准库 → 第三方库 → 本地模块，组间空一行。
- 使用类型注解（Type Hints），公共函数必须标注参数与返回类型。
- 优先使用 f-string 进行字符串格式化。

## 四、项目结构约定

- `routers/`：路由层，仅负责参数校验与响应封装，不写业务逻辑。
- `services/`：业务逻辑层，可复用、可测试，不直接依赖 Web 框架对象。
- `models.py`：ORM 数据模型定义。
- `schemas.py`：Pydantic 请求/响应模型。
- `common/`：通用工具与统一响应封装。

## 五、异常与日志

- 使用统一的异常处理与响应结构，避免把原始堆栈直接暴露给前端。
- 关键业务节点须记录日志，日志包含请求标识、关键参数与耗时。
- 日志级别：DEBUG 调试、INFO 正常流程、WARNING 可恢复异常、ERROR 需关注错误。
- 严禁在日志中打印密码、令牌等敏感信息。

## 六、接口设计

- 遵循 RESTful 风格，资源用名词复数，如 `/api/knowledge-bases`。
- 使用合适的 HTTP 状态码，业务错误通过统一响应体的 code/message 表达。
- 分页统一使用 `page` 与 `page_size` 参数，返回 `total` 与 `items`。
- 对外接口必须做参数校验与权限校验。

## 七、安全要求

- 所有外部输入视为不可信，做好校验与转义，防止注入。
- 敏感配置通过环境变量注入，禁止硬编码到代码仓库。
- 密码使用 bcrypt 等强哈希存储，令牌设置合理有效期。

## 八、提交前检查清单

- 通过格式化工具（如 black / ruff）检查
- 关键逻辑有单元测试覆盖
- 无调试用 print 与注释掉的死代码
- 更新相关文档与接口说明
